# Private YouTube summaries need a thin custom skill

No open-source tool, plugin, Claude skill or MCP server found as of October 2026 does all three things you need: fetch a private video with your own account's cookies, fall back to local Whisper when there are no captions, and produce a structured long-form summary document. Several tools do two of the three. **steipete/summarize** (6.7k stars, active) and the **liang121/video-summarizer** Claude skill come closest, with cookie pass-through plus a Whisper fallback. Neither produces a PDF, neither documents private-video access as a tested feature, and liang121 transcribes with faster-whisper, which runs on the CPU only on a Mac. The most popular YouTube MCP servers only scrape captions, and they fail on both private and caption-less videos. The one practical authenticated route is yt-dlp with browser cookies, since yt-dlp removed OAuth in November 2024 and youtube-transcript-api has turned cookie auth off. The pipeline you already ran by hand on the 4-hour public stream (yt-dlp, mlx-whisper turbo, phantom-line filtering, PDF) is already better than any existing tool for an 8 GB Apple Silicon Mac. The recommendation is to wrap that pipeline in a small Claude Code skill and add three things: cookies applied only when a video needs them, a captions-first check, and the hallucination filter built in rather than applied by hand afterwards. None of these tools has been tested against a real private video, including the one proposed here, so the first job is a hands-on test with one video you own.

## Caption-scraping MCP servers fail on both hard cases

The YouTube MCP ecosystem splits three ways, and only one branch can see private videos. **Caption scrapers** are the most popular and include kimtaeyoon83/mcp-server-youtube-transcript (602 stars), jkawamoto/mcp-youtube-transcript (489) and anaisbetts/mcp-youtube (550). They read YouTube's existing caption tracks, document no cookie support, and have no audio fallback ([kimtaeyoon83](https://github.com/kimtaeyoon83/mcp-server-youtube-transcript); [jkawamoto](https://github.com/jkawamoto/mcp-youtube-transcript)). Several say outright that they can't do what you need. coyaSONG's README says "private, region-restricted, or caption-disabled videos may not return a transcript" ([coyaSONG](https://github.com/coyaSONG/youtube-mcp-server)), and umbertotancorre's says it "only accesses publicly available YouTube data" ([umbertotancorre](https://github.com/umbertotancorre/youtube-mcp-cli)). Many of these servers are built on youtube-transcript-api, which carries a deeper problem. Its README says recent YouTube changes broke cookie authentication, "so this feature is currently not available" ([youtube-transcript-api](https://github.com/jdepoix/youtube-transcript-api#cookie-authentication)). Since April 2026 it has also failed with `PoTokenRequired` on some caption tracks, which a valid cookie session does not fix ([issue #592](https://github.com/jdepoix/youtube-transcript-api/issues/592)).

**Data API servers** such as ZubeidHendricks/youtube-mcp-server (584 stars) use API keys, so they return metadata and nothing more ([ZubeidHendricks](https://github.com/ZubeidHendricks/youtube-mcp-server)). Even with OAuth, the official `captions.download` endpoint "requires the user to have permission to edit the video" and costs **200 quota units** per call. It therefore serves owners only, never someone a video was shared with, and the API has no audio download at all ([YouTube Data API](https://developers.google.com/youtube/v3/docs/captions/download)).

**yt-dlp-based servers** are the only branch that documents cookie access. kevinwatt/yt-dlp-mcp (290 stars) accepts `YTDLP_COOKIES_FROM_BROWSER` or a cookie file "to access private videos" but leaves transcription to the client ([cookies.md](https://github.com/kevinwatt/yt-dlp-mcp/blob/main/docs/cookies.md)). format37/youtube_mcp is the only MCP found that combines cookies with Whisper. It is a Docker server, sends every video to the paid OpenAI API without checking for captions first, and has not been updated since July 2025 ([format37](https://github.com/format37/youtube_mcp)).

## Two near-misses come close and stop short

The full captions-then-Whisper logic lives in skills and standalone CLIs, not MCPs. Anthropic's own skills repo has no YouTube skill ([anthropics/skills](https://github.com/anthropics/skills)).

The strongest case for not building anything is steipete/summarize. It is actively maintained (release v0.25.2 on 2026-10-11) and its `--youtube auto` mode tries the youtubei and caption tracks first, then yt-dlp audio with local whisper.cpp. It can also use Claude Code as its LLM ([README](https://github.com/steipete/summarize)). Three things count against it for your case. Its cookies reach only the yt-dlp path, so the caption fetch runs unauthenticated, and on a private video that step fails before any fallback starts. It transcribes locally with whisper.cpp, which was **about 2x slower than mlx-whisper** on the same turbo model in a January 2026 benchmark ([Bill Mill](https://notes.billmill.org/dev_blog/2026/01/updated_my_mlx_whisper_vs._whisper.cpp_benchmark.html)). And its output is a short summary, not a structured long-form report. liang121's skill has a similar engine problem. faster-whisper supports only NVIDIA GPUs ([faster-whisper](https://github.com/SYSTRAN/faster-whisper)), so on your Mac a 4-hour file would run on the CPU, far slower than the roughly 18 minutes your mlx-whisper run took. That skill has also had no update since January 2026.

## Cookies are the only working key, and they carry account risk

For any video your account can watch but the public cannot, yt-dlp needs that account's cookies, either from `--cookies-from-browser` or a Netscape-format cookie file. OAuth support was removed as broken in release 2024.11.18, and the yt-dlp wiki now says to "use cookies instead" ([Extractors wiki](https://github.com/yt-dlp/yt-dlp/wiki/Extractors)). Several 2025–2026 changes affect how this works in practice. Since yt-dlp 2025.11.12, full YouTube support needs a JavaScript runtime. Deno is the default, and Node needs `--js-runtimes node` and version **22 or later**, which matches what already worked for you ([EJS wiki](https://github.com/yt-dlp/yt-dlp/wiki/EJS)). Signing in also changes which YouTube clients yt-dlp uses, to `web_embedded,tv_samsung,web` on a free account. Some of those clients need PO tokens, so a signed-in download can return 403 errors or missing formats unless the `bgutil-ytdlp-pot-provider` plugin is installed ([yt-dlp README](https://github.com/yt-dlp/yt-dlp/blob/master/README.md); [PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)).

Two failure modes need handling. The first is an expired session. YouTube "rotates account cookies frequently on open YouTube browser tabs". The wiki's fix is to export cookies from a private window that is never reopened, and plain `--cookies-from-browser` cannot read cookies from a private window ([Extractors wiki](https://github.com/yt-dlp/yt-dlp/wiki/Extractors)). The second is the wrong account. If a browser is signed into several Google accounts and the authorized one is not the default, yt-dlp still reports "This video is private" ([issue #6299](https://github.com/yt-dlp/yt-dlp/issues/6299)).

The account risk is real. The wiki warns that an account used with yt-dlp may be **banned temporarily or permanently**. It suggests keeping request rates low and using an account only when necessary ([Extractors wiki](https://github.com/yt-dlp/yt-dlp/wiki/Extractors)). The usual advice to use a throwaway account does not work for private videos unless the owner shares the video with that account through "Share privately" ([YouTube Help](https://support.google.com/youtube/answer/157177?hl=en)). Policy is grey even for videos you own. The YouTube Terms forbid downloading unless "expressly authorized by the Service" and forbid automated access ([YouTube ToS](https://www.youtube.com/t/terms)). For owners, the clearly authorized routes are Studio's MP4 download (720p or 360p, at most five downloads per video per day) and Google Takeout ([Studio download](https://support.google.com/youtube/answer/56100?hl=en); [Takeout](https://support.google.com/accounts/answer/3024190?hl=en)). Either file can go straight into the transcription step.

One case is simpler than it looks. Anyone with the link can watch an unlisted video, so an unlisted video should not need cookies at all. Cookies matter for truly private videos, and the skill should send them only after an anonymous attempt fails. That follows the wiki's advice to use an account only when needed, and it keeps your real account out of most runs. Whether yt-dlp can download captions for a private video with cookies is **undocumented**. It should work the same way as for a public video once the signed-in player response is fetched, but no source confirms it ([access notes, PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)).

## Your 18-minute run is the best Apple Silicon data point available

Researchers found no published benchmark of any engine on 1–4 hours of audio on an 8 GB Mac. Your run fills that gap: about 18 minutes to transcribe 4 hours with whisper-large-v3-turbo on mlx-whisper, which is about 13x realtime. The published data supports that choice. Turbo is large-v3 with the decoder cut from 32 layers to 4, "way faster, at the expense of a minor quality degradation" ([model card](https://huggingface.co/openai/whisper-large-v3-turbo)). mlx-whisper is the fastest maintained Whisper runtime on Apple Silicon and writes txt, vtt, srt and json ([mlx_whisper CLI](https://raw.githubusercontent.com/ml-explore/mlx-examples/main/whisper/mlx_whisper/cli.py)). Its weakness is the one you hit. Whisper fills silence with YouTube-style sign-offs, and "thank you" is the most common output on non-speech audio at **24.76%** ([Dograh summary of arXiv 2501.11378](https://www.dograh.com/feeds/blog/whisper-hallucination-silence)). mlx-whisper has no built-in voice-activity detection. Its closest guard is `--hallucination-silence-threshold`, which works only with `--word-timestamps True` ([cli.py](https://raw.githubusercontent.com/ml-explore/mlx-examples/main/whisper/mlx_whisper/cli.py)). So the skill should use that flag and also filter known phantom phrases and collapse repeated segments afterwards.

parakeet-mlx (NVIDIA Parakeet TDT 0.6B v3) is the one engine that could beat your setup. It is smaller, splits long audio into chunks by default, and reports 6.34% average word error rate. It covers only **25 European languages**, though ([parakeet-mlx](https://github.com/senstella/parakeet-mlx); [model card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3)). Whether it hallucinates less than Whisper has not been verified. At 18 minutes per 4-hour file, speed is not your bottleneck, so Parakeet is an option to keep in reserve, not a reason to change. Cloud transcription is cheap if the Mac is busy, from **$0.15/hour** on AssemblyAI Universal-2 ([AssemblyAI](https://www.assemblyai.com/pricing)). It would mean uploading audio from a private video to a third party, which defeats much of the point of a private-video tool.

## What the skill should look like

Build a Claude Code skill, not an MCP server. It runs where you work, it can use the shell, and Claude itself writes the summary, so no LLM API key is needed. The skill is a `SKILL.md` plus one Python script run with `uv run`, with PDF rendering through reportlab as before. Each stage below comes from the existing tools or your run, and the gaps they leave are noted.

| Stage | Behaviour | Why |
|---|---|---|
| Input | A YouTube URL or a local media file (from Studio or Takeout) | Local files are the clearly authorized route for videos you own |
| Probe | `yt-dlp -J` without cookies, then with `--cookies-from-browser firefox` or a cookies.txt only if the probe fails | Keeps the account out of runs that don't need it, as the wiki advises |
| Captions | `--write-subs --write-auto-subs --sub-langs "en.*" --skip-download`, using the same cookie setting | Captions are faster and cheaper than transcription |
| Audio fallback | `-f bestaudio`, then convert once to 16 kHz mono WAV with the imageio-ffmpeg binary | The setup that already worked for you |
| Transcribe | mlx-whisper turbo, `--condition-on-previous-text False --word-timestamps True --hallucination-silence-threshold 2 -f json` | Prevents repetition loops and skips silence |
| Clean | Drop phantom sign-off lines and collapse consecutive repeats | Removes the "Thank you." lines you filtered by hand |
| Summarize | Claude summarizes the transcript in timestamped chunks, then merges them into a fixed Markdown template | A 4-hour transcript is too long to summarize well in one pass |
| Render | Markdown to PDF | No existing YouTube tool produces a PDF |

Three error messages need to be specific, because they cover the cases that fail without explanation. "Private even with cookies" should tell the user to check which account is the browser's default. A 403 on a signed-in download should suggest the bgutil PO-token plugin. "Sign in to confirm" should suggest re-exporting cookies. Leave out speaker diarization, Data API OAuth and Parakeet until a real video needs them. Diarization ran at about 24x realtime on an M4 Pro, which will be slower on an 8 GB M1, and it needs a gated Hugging Face model ([speakrs](https://docs.rs/speakrs)). Data API OAuth costs about 250 quota units per video and works only for videos you own. Before you rely on the skill, run it once on a private video you own and once on one shared with you. No tool in this survey, including this design, has been tested on a real private video.

## Conclusion

The gap is not a missing algorithm. Existing tools treat authentication, transcription engine and output format as separate concerns, and each tool gets one of them wrong for this setup. Caption MCPs can't sign in, the cookie-aware skills use engines that are slow on a Mac, and the best CLI produces short summaries. Your setup needs the narrowest version of each: yt-dlp cookies, MLX, and Claude writing the summary. That makes a custom skill of a few hundred lines a better fit than adopting a larger tool and working around it.

The larger risks are outside the code. The tool cannot fix cookie rotation, PO-token changes or a possible account ban. The design limits exposure by trying without cookies first, but YouTube can still break the cookie path, as it has before. For videos you own, the most reliable path that keeps you within YouTube's terms is a Studio or Takeout download fed into the same pipeline. The skill should treat that as an equal input, not a fallback.
